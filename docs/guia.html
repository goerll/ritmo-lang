O compilador .ritmo por dentro

Este guia percorre o compilador inteiro, na ordem em que o código-fonte passa por ele. Para cada fase, explica o que ela faz, por que foi feita assim e qual trecho do código responde por ela. O objetivo é você conseguir defender cada decisão como se tivesse escrito tudo à mão.

A ideia em uma frase

O programa lê um arquivo .ritmo, que descreve música em ciclos e padrões no estilo do TidalCycles e do Strudel. Ele verifica se o programa está correto e o traduz para um script Python que chama funções de uma pequena biblioteca de padrões e síntese de áudio. Em seguida, executa esse script na hora, que gera o .wav e toca o som.

Por que isso é um compilador, e não só um interpretador O programa nunca "toca" a árvore diretamente. Ele traduz para outra linguagem (Python) e depois executa a tradução. Esse é o modelo de um transpilador (compilador fonte-para-fonte). O requisito de one-step pipeline é cumprido porque a tradução e a execução acontecem no mesmo comando: o usuário nunca vê o Python, a menos que peça com --emitir.

Como rodar

cd ~/dsl-musical
.venv/bin/python main.py exemplos/demo.ritmo                  # compila, gera o .wav e toca
.venv/bin/python main.py exemplos/demo.ritmo --mostrar-ast    # imprime a AST e para
.venv/bin/python main.py exemplos/demo.ritmo --mostrar-arvore # árvore de derivação do Lark
.venv/bin/python main.py exemplos/demo.ritmo --emitir out.py  # salva o Python gerado
.venv/bin/python main.py exemplos/demo.ritmo --sem-tocar      # só gera o .wav
.venv/bin/python -m pytest testes                             # 71 testes

Sugestão de leitura: faça um passe rápido pelas seções 01 a 03, brinque no laboratório e depois leia as fases com o código aberto ao lado. A seção 13 reúne as perguntas mais prováveis da banca.

01

A linguagem

Antes do compilador, a linguagem que ele aceita. Tudo gira em torno de um conceito: o ciclo.

Ciclos

Um ciclo é um compasso de 4 tempos. Com tempo 120; (BPM), cada tempo dura 0,5 s e cada ciclo dura 240 / bpm = 2 s. Todo o tempo interno do compilador é medido em ciclos, não em segundos. Os segundos só aparecem no último passo, a síntese de áudio.

Um padrão descreve o que acontece dentro de um ciclo e se repete a cada ciclo. Dentro dele, o tempo é dividido igualmente entre os elementos: [bd sd hh hh] tem 4 passos, cada um ocupando ¼ do ciclo.

Um programa completo

// demo.ritmo
tempo 120;                                   // configuração (BPM)

instrumento lead  { onda quadrada; volume 0.5; }   // declaração de instrumento
instrumento grave { onda serra;    volume 0.7; }

padrao groove = [bd ~ sd ~, hh*8];           // padrão nomeado (reutilizável)

faixa percussao: bateria groove;             // faixa de bateria, usando o padrão
faixa baixo:   nota [c2 ~ c2 <eb2 g2>] com grave .lento(2);
faixa melodia: nota [c4 e4 [g4 a4] <b4 c5>] com lead .transpor(12) .volume(0.6);

tocar 8 ciclos salvar "demo.wav";             // comando final

Transformações de faixa

Vêm depois da fonte, com ponto, e são aplicadas na ordem, da esquerda para a direita: .rapido(n), .lento(n), .reverso(), .transpor(semitons) e .volume(x).

O fluxo em código

      
A função compilar em main.py é o resumo do projeto inteiro:


def compilar(fonte: str, nome: str, *, reproduzir=True, arquivo_padrao="saida.wav"):
    """Fonte -> (AST, resultado semântico, código Python). Lança erros de compilação."""
    prog = analisar(fonte)                       # léxico + sintático -> AST
    resultado = analisar_semantica(prog)         # semântico
    codigo = gerar(prog, resultado.tabela, nome_fonte=nome,
                   reproduzir=reproduzir, arquivo_padrao=arquivo_padrao)
    return prog, resultado, codigo


def executar(codigo: str, nome: str):
    escopo = {"__name__": "__main__", "__file__": nome}
    exec(compile(codigo, f"<gerado de {nome}>", "exec"), escopo)

      
Se qualquer fase falha, ela lança uma exceção (ErroLexico, ErroSintatico ou ErrosSemanticos). O main a captura, imprime a mensagem formatada e retorna código de saída 1. Nada é gerado nem executado.

    

  


  
  

    

      
04
Fase 1 · Análise léxica
gramatica.lark (terminais) · parser.py

      
O analisador léxico (lexer, scanner) transforma a sequência de caracteres numa sequência de tokens. Cada token tem um tipo (NOTA, NUMERO, ID…) e um lexema (o texto exato, como c4 ou 120). Espaços e comentários são descartados aqui.


      
Exemplo real

      
A linha faixa baixo: nota [c2 ~ <eb2 g2>] com grave .lento(2); vira, no Lark:


FAIXA 'faixa'  ID 'baixo'  COLON ':'  NOTA_KW 'nota'  LSQB '['  NOTA 'c2'  TILDE '~'
LESSTHAN '<'  NOTA 'eb2'  NOTA 'g2'  MORETHAN '>'  RSQB ']'  COM 'com'  ID 'grave'
DOT '.'  ID 'lento'  LPAR '('  NUMERO '2'  RPAR ')'  SEMICOLON ';'

      
Os nomes LSQB, TILDE, COLON etc. são os nomes automáticos que o Lark dá aos símbolos literais da gramática. Palavras reservadas viram tokens com o próprio nome em maiúsculas (FAIXA, COM).


      
Os terminais


NOTA.3   : /[a-g](#|b)?[0-9](?![A-Za-z0-9_#])/      // c4, f#3, eb2, b3, bb3
SOM.3    : /(bd|sd|hh|oh|cp)(?![A-Za-z0-9_])/       // bateria sintetizada
ONDA.3   : /(senoide|quadrada|serra|triangulo)(?![A-Za-z0-9_])/

NOTA_KW  : "nota"
BATERIA_KW : "bateria"
VOLUME   : "volume"

NUMERO   : /-?[0-9]+(\.[0-9]+)?/
STRING   : /"[^"\n]*"/
ID       : /[a-zA-Z_][a-zA-Z0-9_]*/

COMENTARIO : /\/\/[^\n]*/
%import common.WS
%ignore WS
%ignore COMENTARIO


      
Lendo as expressões regulares

      
    
        
  • [a-g](#|b)?[0-9]: uma letra de a a g, opcionalmente # ou b, e um dígito. Por isso b3 é si 3 e bb3 é si bemol 3: o primeiro b é a letra e o segundo é o acidente.
    • 
        
  • -?[0-9]+(\.[0-9]+)?: inteiro ou decimal, com sinal opcional (necessário para .transpor(-12)).
    • 
        
  • %ignore WS e %ignore COMENTARIO: o lexer reconhece espaços e comentários, mas não os entrega ao parser.
    • 
      


      
Os conflitos léxicos e como foram resolvidos

      
Esta é uma das partes mais "de compiladores" do trabalho, então vale entender bem. Vários terminais podem casar com o mesmo texto:

      

        
TextoPoderia serÉMecanismo

        
          
c4NOTA ou IDNOTAprioridade .3 (padrão é 0)

          
bdSOM ou ID (nunca NOTA, falta o dígito)SOMprioridade .3

          
tempopalavra reservada ou IDreservadao Lark dá preferência a literais de string que colidem com um regex

          
temposreservada tempo + s, ou IDIDo Lark só aplica a reservada se o lexema inteiro for igual

          
c4e4NOTA c4 + NOTA e4, ou IDID (e erro sintático)lookahead negativo (?![A-Za-z0-9_#])

          
serroteONDA serra + te, ou IDIDlookahead negativo

        
      


      
O lookahead negativo, explicado
      (?!X) numa regex significa "só case se o que vem logo depois não for X", sem consumir nada. Sem ele, a prioridade da NOTA faria c4x ser lido como NOTA c4 seguida de ID x: o lexer pegaria só o prefixo. Com ele, a NOTA só casa quando a palavra termina ali. Assim c4x vira um ID inteiro, que o parser rejeita com uma mensagem clara e a dica "separe os passos com espaços".


      
O lexer contextual e a função _id

      
O Lark com LALR usa por padrão um lexer contextual: em cada estado do parser, ele só tenta os terminais que aquele estado aceita. Isso ajuda (por exemplo, volume pode ser palavra reservada dentro de instrumento e nome de transformação depois do ponto), mas tem um efeito colateral. Onde só cabe um ID, como em padrao ___ =, o lexer aceitaria tocar, bd ou c4 como nome, porque os terminais concorrentes nem são tentados naquele estado.

      
A especificação diz que reservadas, notas e sons têm prioridade sobre ID. Por isso o parser faz uma checagem explícita sempre que constrói um identificador:


RESERVADAS = {"tempo", "instrumento", "onda", "volume", "padrao", "faixa",
              "nota", "bateria", "com", "tocar", "ciclos", "salvar"}
_RE_NOTA = re.compile(r"[a-g](#|b)?[0-9]")
_SONS = {"bd", "sd", "hh", "oh", "cp"}

def _id(tok: Token) -> str:
    nome = str(tok)
    if nome in RESERVADAS:
        motivo = "é palavra reservada"
    elif nome in _SONS:
        motivo = "é um som de bateria"
    elif _RE_NOTA.fullmatch(nome):
        motivo = "é uma nota"
    else:
        return nome
    raise ErroSintatico(f"'{nome}' {motivo} e não pode ser usado como identificador",
                        tok.line, tok.column, len(tok))

      
Como explicar"O lexer contextual do Lark só considera os tokens válidos no estado atual. Isso é bom para volume, que é reservada e também nome de transformação, mas deixaria passar tocar como identificador. Para manter a regra da especificação, rejeito explicitamente reservadas, notas e sons onde se espera um ID. Um teste cobre esse caso."


      
Erros léxicos

      
Quando nenhum terminal casa com o caractere atual, o Lark lança UnexpectedCharacters, que o parser converte em ErroLexico com linha e coluna. Uma aspa sem fechamento tem mensagem especial:


exemplos/erros/lexico_caractere.ritmo:2:22: erro léxico: caractere inesperado '$'
 2 | faixa a: bateria [bd $ sd];
   |                      ^

    

  


  
  

    

      
05
Fase 2 · Análise sintática
gramatica.lark (regras) · parser.py

      
O analisador sintático (parser) verifica se a sequência de tokens segue a gramática e constrói a árvore de derivação, que mostra qual regra gerou cada pedaço do texto.


      
A gramática formal (EBNF)


programa        ::= { declaracao }
declaracao      ::= cfg_tempo | def_instrumento | def_padrao | faixa | tocar

cfg_tempo       ::= "tempo" NUMERO ";"
def_instrumento ::= "instrumento" ID "{" { propriedade ";" } "}"
propriedade     ::= "onda" ONDA | "volume" NUMERO
def_padrao      ::= "padrao" ID "=" padrao ";"
faixa           ::= "faixa" ID ":" fonte { transformacao } ";"
fonte           ::= ("nota" | "bateria") (padrao | ID) [ "com" ID ]
transformacao   ::= "." (ID | "volume") "(" [ NUMERO ] ")"
tocar           ::= "tocar" NUMERO "ciclos" [ "salvar" STRING ] ";"

(* mini-notação: da MENOR para a MAIOR precedência *)
padrao          ::= "[" camadas "]"
camadas         ::= sequencia { "," sequencia }
sequencia       ::= passo { passo }
passo           ::= atomo { modificador }
modificador     ::= "*" NUMERO | "/" NUMERO
atomo           ::= NOTA | SOM | "~" | "[" camadas "]" | "<" sequencia ">"

      
Notação: { x } é zero ou mais repetições, [ x ] é opcional e | é alternativa. Entre aspas ficam os terminais literais.

      
A gramática cobre os itens que o professor pediu: estrutura dos comandos (as 5 declarações), tipos de dados (NUMERO, NOTA, SOM, ONDA, STRING, padrão), identificadores (ID), delimitadores (; { } [ ] < > ( ) : , .) e precedência (os níveis da mini-notação).


      
A mesma gramática na notação do Lark


programa        : declaracao*

?declaracao     : cfg_tempo | def_instrumento | def_padrao | faixa | tocar

propriedade     : "onda" ONDA           -> prop_onda
                | VOLUME NUMERO         -> prop_volume

fonte           : tipo_fonte (padrao | ID) ["com" ID]

camadas         : sequencia ("," sequencia)*
sequencia       : passo+
passo           : atomo modificador*

?modificador    : "*" NUMERO            -> mod_rapido
                | "/" NUMERO            -> mod_lento

?atomo          : NOTA                  -> nota
                | SOM                   -> som
                | "~"                   -> pausa
                | "[" camadas "]"       -> grupo
                | "<" sequencia ">"     -> alterna

      
    
        
  • ?regra: regra "inline". Se ela tiver um único filho, o nó desaparece da árvore e o filho sobe. Por isso não aparece um nó declaracao envolvendo cada declaração.
    • 
        
  • -> nome: apelido. Cada alternativa vira um nó com nome próprio (nota, pausa, mod_rapido), e o Transformer tem um método para cada um.
    • 
        
  • [x] versus x?: com maybe_placeholders=True, um [x] ausente vira None na lista de filhos, e x? simplesmente some. Isso permite desempacotar os filhos com segurança (tipo, conteudo, instr = filhos).
    • 
        
  • Literais anônimos como "faixa" e ";" são filtrados da árvore. Só sobram os terminais nomeados, que carregam informação.
    • 
      


      
Como a precedência é codificada

      
Não existe uma "tabela de precedência" no código. A precedência está na forma da gramática, numa escada de níveis: cada nível só pode conter elementos do nível de baixo. Quanto mais fundo o nível, mais forte ele "gruda".

      

        
NívelRegraOperadorForça

        
          
1 (mais externo)camadas,liga mais fraco

          
2sequenciajustaposição (espaço)médio

          
3passo*n /n (pós-fixos)liga mais forte

          
4 (folhas)atomo[ ] e < > reiniciam a escada—

        
      

      
Exemplo: [bd sd*2, hh]. A vírgula é o nível mais externo, então ela separa primeiro: (bd sd*2) e (hh). Dentro da primeira sequência, o *2 é pós-fixo, então se prende só ao sd. Resultado: ((bd (sd*2)), hh). Veja a árvore de derivação real produzida pelo Lark (--mostrar-arvore):


camadas
  sequencia
    passo
      som     bd
    passo
      som     sd
      mod_rapido  2        ← o *2 está DENTRO do passo do sd
  sequencia                ← a vírgula separou duas sequências
    passo
      som     hh

      
É o mesmo princípio de expr → termo → fator nas gramáticas de expressões aritméticas, onde * liga mais forte que + porque fica num nível mais fundo.


      
Associatividade

      
    
        
  • Modificadores pós-fixos: bd*2/3 é (bd*2)/3. A regra atomo modificador* lê os modificadores da esquerda para a direita, e o Transformer os aplica nessa ordem, cada um envolvendo o resultado anterior (veja a seção 06).
    • 
        
  • Transformações: .transpor(12).volume(0.6) vira volume(0.6, transpor(12, p)), ou seja, associativas à esquerda e aplicadas em ordem.
    • 
        
  • Modificadores só valem dentro de colchetes. [bd sd]*2 é erro sintático, porque depois do ] do padrão a gramática espera com, . ou ;. O certo é [[bd sd]*2] ou .rapido(2).
    • 
      


      
Por que LALR(1)

      
O Lark oferece dois algoritmos: Earley, que aceita qualquer gramática livre de contexto, inclusive ambígua, mas é mais lento, e LALR(1). Escolhi LALR(1) por quatro motivos:

      
    
        
  1. A gramática é determinística. Com um único token de lookahead dá para decidir cada passo. Se não fosse, o Lark recusaria a gramática já na construção, acusando conflito shift/reduce ou reduce/reduce. Ou seja, o próprio Lark prova que a gramática não é ambígua.
    2. 
        
  2. É linear no tamanho da entrada.
    3. 
        
  3. Permite o lexer contextual, que resolve o caso do volume.
    4. 
        
  4. Dá mensagens de erro precisas, com o conjunto exato de tokens esperados.
    5. 
      

      
Como o LALR funciona, em 4 frases
      É um parser ascendente (bottom-up): lê tokens da esquerda para a direita e os empilha (shift). Quando o topo da pilha forma o lado direito de uma regra, ele o substitui pelo não terminal (reduce). Uma tabela pré-calculada a partir da gramática, consultada com o estado atual mais 1 token de lookahead, diz se é hora de shift, de reduce ou de erro. A árvore é montada de baixo para cima, das folhas até programa.

      
A gramática também é praticamente LL(1). Daria para escrever um parser descendente recursivo à mão, com uma função por regra, e o laboratório da seção 02 faz exatamente isso em JavaScript para a mini-notação. Vale mencionar na apresentação: mostra que você entende as duas abordagens.


      
Erros sintáticos

      
O Lark lança UnexpectedToken (ou UnexpectedEOF), e o parser converte em ErroSintatico. Duas melhorias foram feitas:

      
    
        
  • Lista exata de esperados. O LALR às vezes faz reduções "por padrão" antes de perceber o erro, e o conjunto e.expected fica maior do que deveria. Por isso o parser consulta o interactive_parser.accepts(), que diz exatamente quais tokens seriam aceitos naquele ponto.
    • 
        
  • Dicas. Por exemplo, se um ; era esperado e o token inesperado está na coluna 1, a dica é "faltou ';' no fim da linha anterior?".
    • 
      


exemplos/erros/sintatico_ponto_virgula.ritmo:3:1: erro sintático: token inesperado 'tocar'; esperado: '.', ';', 'com'
 3 | tocar 2 ciclos;
   | ^^^^^
   = dica: faltou ';' no fim da linha anterior?

Fase 3 · A AST
parser.py (ConstrutorAST) · ast_nos.py

      
A árvore de derivação do Lark é concreta: ela espelha a gramática, com nós como passo, tipo_fonte e padrao, e guarda tokens soltos. A AST (árvore sintática abstrata) guarda só o que importa para o significado, com nós tipados e posição no código.

O Transformer: de árvore concreta para AST

      
O ConstrutorAST é um lark.Transformer. Para cada nó da árvore concreta, ele chama o método com o mesmo nome da regra (ou do apelido), passando os filhos já transformados. O percurso é de baixo para cima (pós-ordem), como num esquema de tradução dirigida pela sintaxe com atributos sintetizados.


@v_args(meta=True)                      # cada método recebe (meta, filhos); meta tem linha/coluna
class ConstrutorAST(Transformer):

    def nota(self, meta, filhos):
        return A.Nota(str(filhos[0]), _pos_tok(filhos[0]))

    def grupo(self, meta, filhos):      # "[" camadas "]"  → devolve as camadas; os colchetes somem
        return filhos[0]

    def fonte(self, meta, filhos):
        tipo, conteudo, instr = filhos  # graças a maybe_placeholders, instr pode ser None
        ...

    def passo(self, meta, filhos):
        no, *mods = filhos              # átomo + modificadores, na ordem do texto
        for tipo, args, pos in mods:    # dobra à esquerda: cada modificador envolve o anterior
            if tipo == "rapido":
                no = A.Rapido(args[0], no, pos)
            elif tipo == "lento":
                no = A.Lento(args[0], no, pos)
        return no

      
O método passo é onde a associatividade à esquerda dos modificadores vira estrutura. Para bd*2/3, o laço faz primeiro Rapido(2, bd) e depois Lento(3, Rapido(2, bd)).

      
Os métodos dos modificadores (mod_rapido, mod_lento…) não criam nós. Eles devolvem tuplas ("rapido", [Numero], pos), que o passo consome. Assim o nó só é criado quando já se sabe quem é o alvo.

Uma gramática livre de contexto só verifica a forma. Ela não consegue checar coisas como "este instrumento foi declarado?", "este padrão tem notas, mas a faixa é de bateria" ou "volume 1.5 está fora do intervalo". Inferência do "tipo" de um padrão

      
Um padrão é um tipo composto, e seu conteúdo é de notas ou de sons de bateria. A função _tipo_padrao coleta todas as folhas da subárvore (Nota e Som) e compara cada uma com a primeira:


def _tipo_padrao(self, raiz):
    folhas = []
    self._percorrer(raiz, folhas)        # também valida *0 e /0
    tipo, primeira = None, None
    for f in folhas:
        t = "nota" if isinstance(f, A.Nota) else "bateria"
        if tipo is None:
            tipo, primeira = t, f
        elif t != tipo:
            self.erros.append(_erro(f"padrão mistura ... : '{nome}'", f.pos, dica))
            break
    return tipo                          # None se só houver pausas

Runtime · modelo de padrões
runtime/padroes.py

      
É aqui que a música acontece. O modelo vem do TidalCycles e é muito elegante: um padrão é uma função.


class Evento(NamedTuple):
    inicio: Fraction
    fim: Fraction
    valor: Any                  # Valor("nota", "c4", midi=60, ganho=1.0)

class Padrao:
    def __init__(self, consulta):   # consulta(inicio, fim) -> [Evento]
        self.consulta = consulta

      
Perguntar a um padrão "o que acontece entre os ciclos 0 e 2?" é chamar p.query(0, 2). Cada combinador recebe padrões e devolve um novo padrão, uma nova função de consulta que chama as consultas dos filhos e transforma os eventos. Nada é calculado até alguém consultar (avaliação preguiçosa).


      
Regra simplificada de consulta
      query(a, b) devolve os eventos cujo início está em [a, b). Cada evento carrega a duração inteira. No Tidal original, um evento que atravessa o limite da consulta é devolvido em pedaços ("fragmentos"). Essa simplificação evita fragmentos e é suficiente porque a renderização consulta [0, N) de uma vez.


      
Por que Fraction

      
Em [a [b c d]], os passos internos começam em ½, ⅔ e ⅚ do ciclo. Em float, ⅓ é 0,333…, e somar ou multiplicar acumula erro. Depois de 100 ciclos, eventos que deveriam coincidir deixariam de coincidir. Com fractions.Fraction, ⅓ é exatamente 1/3. Os tempos só viram float na síntese, quando são multiplicados pela duração do ciclo em segundos.


      
Os combinadores, um a um


      
pure(v): o átomo


def pure(valor):
    def consulta(a, b):
        return [Evento(Fraction(c), Fraction(c + 1), valor)
                for c in _ciclos(a, b) if a <= c < b]
    return Padrao(consulta)

      
Um evento ocupando cada ciclo inteiro: (0,1), (1,2), (2,3)… _ciclos(a, b) é range(floor(a), ceil(b)). nota("c4") e som("bd") são pure de um Valor.


      
rapido(n, p): comprimir o tempo


def rapido(fator, p):
    n = _frac(fator)
    def consulta(a, b):
        return [Evento(e.inicio / n, e.fim / n, e.valor) for e in p.consulta(a * n, b * n)]
    return Padrao(consulta)

      
Para saber o que p*4 faz em [0, 1), pergunta-se ao p original o que acontece em [0, 4) e divide-se os tempos por 4: quatro eventos de ¼. lento(n, p) é simplesmente rapido(1/n, p).


      
alterna(a, b, c): um filho por ciclo


def alterna(*ps):
    n = len(ps)
    def consulta(a, b):
        saida = []
        for c in _ciclos(a, b):
            filho = ps[c % n]
            desloc = c - c // n          # ciclo c do pai = ciclo c//n do filho
            ini, fim = max(a, c), min(b, c + 1)
            for e in filho.consulta(ini - desloc, fim - desloc):
                saida.append(Evento(e.inicio + desloc, e.fim + desloc, e.valor))
        return saida
    return Padrao(consulta)

      
A parte sutil é o desloc. Cada filho "vê" só os ciclos em que está ativo, numerados 0, 1, 2… do ponto de vista dele. Com 2 filhos, o filho 0 toca nos ciclos 0, 2, 4 do pai, que para ele são os ciclos 0, 1, 2.

    

    

      
ciclo do pai cfilho c % 2ciclo do filho c // 2desloc = c − c//2

      
        
0000

        
1101

        
2011

        
3112

        
4022

      
    

    

      
É isso que faz <a <b c>> soar a b a c. O filho interno <b c> só é consultado nos ciclos 1 e 3 do pai, que para ele são os ciclos 0 e 1, então ele alterna corretamente entre b e c.


      
seq(a, b, c): a sacada


def seq(*ps):
    return rapido(len(ps), alterna(*ps))

      
Uma sequência de n elementos é uma alternância de n elementos, acelerada n vezes. Exemplo: seq(a, b) no ciclo 0. O rapido(2) consulta a alternância em [0, 2): ciclo 0 → a em (0,1), ciclo 1 → b em (1,2). Dividindo por 2: a em (0, ½) e b em (½, 1). ✔

      
A consequência importante: uma alternância dentro de uma sequência funciona sozinha. Em [c4 <b4 c5>], no ciclo 1 do pai a alternância externa está nos ciclos 2 e 3, e o <b4 c5> recebe o seu ciclo 1, então toca c5. Não é preciso nenhum caso especial.


      
stack(a, b): polifonia

      
Concatena as listas de eventos de todos os filhos. Simples assim.


      
reverso(p): espelhar cada ciclo


def reverso(p):
    def consulta(a, b):
        saida = []
        for c in _ciclos(a, b):
            eixo = 2 * c + 1                       # t -> (c+1) - (t-c)
            for e in p.consulta(Fraction(c), Fraction(c + 1)):
                fim = min(e.fim, Fraction(c + 1))  # eventos longos são cortados no ciclo
                novo = Evento(eixo - fim, eixo - e.inicio, e.valor)
                if a <= novo.inicio < b:
                    saida.append(novo)
        return saida
    return Padrao(consulta)

      
Dentro do ciclo c, o instante t vai para c + (c+1 − t) = 2c + 1 − t. O fim de um evento vira o novo início. Por exemplo, [bd ~ ~ ~] no ciclo 1: o bd em (1, 5/4) vai para (3 − 5/4, 3 − 1) = (7/4, 2).


      
transpor e volume: mexem no valor

      
Os dois usam fmap(f, p), que aplica f ao valor de cada evento sem tocar no tempo. transpor soma semitons ao MIDI (só para notas) e volume multiplica o ganho.

Cada semitom multiplica a frequência por 21/12, e cada oitava (12 semitons) a dobra.


      
Formas de onda

      
Com fase = freq · t (em ciclos da onda):

      
    
        
  • senoide: sin(2π·fase). Som puro, sem harmônicos.
    • 
        
  • quadrada: sign(sin(2π·fase)). Só harmônicos ímpares, som "oco" de videogame.
    • 
        
  • serra: 2·(fase − round(fase)). Rampa, rica em todos os harmônicos, som brilhante.
    • 
        
  • triângulo: 2·|serra| − 1. Harmônicos ímpares fracos, som suave.
    • 
      


      
Envelope

      
Se uma onda começa ou termina abruptamente num valor diferente de zero, o alto-falante ouve um "clique". Por isso cada nota é multiplicada por um envelope: sobe de 0 a 1 em 5 ms (ataque) e desce de 1 a 0 nos últimos 50 ms (release).


      
Bateria sintetizada

      

        
SomReceita

        
          
bd bumbosenoide cuja frequência cai de 150 para 50 Hz (50 + 100·e−25t), com decaimento exponencial. A fase é a soma acumulada da frequência (cumsum), porque a frequência muda.

          
sd caixaruído branco (a esteira) + senoide de 180 Hz (o corpo), ambos com decaimento curto

          
hh / ohruído passa-alta, feito com a diferença entre amostras vizinhas (np.diff, um filtro passa-alta de primeira ordem). Decaimento muito curto (fechado) ou longo (aberto).

          
cp palma3 rajadas de ruído com 11 ms entre elas + uma cauda, imitando várias mãos

Perguntas do professor

      
Tente responder em voz alta antes de abrir cada uma.


      
Por que traduzir para Python em vez de interpretar a AST?

        
Porque o trabalho pede um compilador/transpilador. Gerar código separa a análise (que garante que o programa está correto) da execução (que fica a cargo do Python e do runtime). O código gerado também é inspecionável com --emitir e roda sozinho, porque é autocontido.


      
O que é o one-step pipeline e como você o cumpre?

        
Um único comando compila e executa. main.py gera o Python como string, chama compile() e exec() em memória. O usuário nunca vê nem edita o Python, e nenhum arquivo intermediário é criado.


      
Por que Lark? Por que LALR e não Earley?

        
O Lark permite que a gramática seja um arquivo separado, o próprio entregável gramatica.lark, e gera o parser a partir dele. Escolhi LALR(1) porque a gramática é determinística (o Lark verificaria conflitos ao construir a tabela), porque é linear e porque permite o lexer contextual. O Earley aceitaria gramáticas ambíguas, o que esconderia erros de projeto da gramática.


      
Onde está a precedência na sua gramática?

        
Na estratificação das regras: camadas contém sequencia, que contém passo, que contém atomo. A vírgula está no nível mais externo e liga mais fraco; os pós-fixos estão no mais interno e ligam mais forte. É a mesma técnica de expr/termo/fator. [bd sd*2, hh] = ((bd (sd*2)), hh).


      
E a associatividade?

        
Modificadores: atomo modificador* lê da esquerda para a direita, e o Transformer, no método passo, envolve cada nó no próximo, o que dá associatividade à esquerda (bd*2/3 = (bd*2)/3). Transformações: o gerador dobra à esquerda, então .a().b() vira b(a(p)).


      
Como o lexer sabe que bd não é identificador e que c4e4 não é duas notas?

        
bd: o terminal SOM tem prioridade 3, maior que o ID. c4e4: o regex da NOTA tem um lookahead negativo (?![A-Za-z0-9_#]), então só casa se a palavra terminar logo depois do dígito. Assim c4e4 inteiro vira ID, e o parser dá erro com a dica de separar os passos com espaços.


      
Se o lexer é contextual, como você impede padrao tocar = [...]?

        
Naquele estado, o lexer contextual só tenta os tokens aceitos, e ID é o único, então tocar viraria ID. Por isso o Transformer passa todo identificador por _id(), que rejeita palavras reservadas, sons e notas com um erro sintático na posição certa. Isso garante a regra da especificação de que as reservadas têm prioridade sobre ID.


      
Qual a diferença entre a árvore de derivação e a AST?

        
A árvore de derivação (concreta) tem um nó para cada regra usada e guarda os tokens. A AST guarda só a estrutura com significado: os nós passo e padrao somem, [ ] vira a própria Camadas, a fonte vira um objeto com campos tipados e cada nó guarda sua posição para as mensagens de erro. Dá para mostrar as duas com --mostrar-arvore e --mostrar-ast.


      
Por que essas verificações são semânticas e não estão na gramática?

        
Porque dependem de contexto ou de valores, e uma gramática livre de contexto não guarda contexto. "O instrumento foi declarado" exige lembrar declarações anteriores (tabela de símbolos). "Volume ≤ 1" é sobre o valor do número, não sobre a forma. "Faixa de som com notas" depende do tipo inferido do padrão, que pode estar declarado em outro lugar.


      
Como funciona sua tabela de símbolos?

        
São três dicionários (instrumentos, padrões e faixas) de nome para informação: o nó da declaração, os atributos resolvidos (onda, volume, tipo do padrão) e uma flag usado para os avisos. Ela é preenchida na primeira passada e consultada na segunda. O gerador também a usa, para pegar a onda e o volume já resolvidos com os valores padrão.


      
Como você infere o tipo de um padrão?

        
Percorro a subárvore e coleto as folhas (Nota e Som). Se todas são do mesmo tipo, esse é o tipo do padrão. Se aparece uma diferente, é erro, apontado para a folha intrusa. Só pausas dá tipo neutro (None), compatível com os dois tipos de faixa. Para padrão nomeado, o tipo é guardado na tabela e comparado com nota/som no ponto de uso.


      
Por que o código gerado chama funções em vez de listar as notas?

        
Para que a tradução preserve a estrutura do programa. Cada nó da AST vira uma chamada de combinador, e dá para apontar a correspondência no --emitir. Pré-calcular transformaria o compilador num gerador de dados, e a semântica das construções (alternância, aceleração) ficaria escondida dentro do compilador.


      
Explique por que seq é rapido(n, alterna(...)).

        
A alternância põe cada filho num ciclo inteiro: filho 0 no ciclo 0, filho 1 no ciclo 1… Acelerando n vezes, esses n ciclos cabem em um, e cada filho fica com 1/n. A vantagem é que alternâncias aninhadas dentro de sequências recebem a contagem de ciclos correta de graça. É exatamente como o Tidal define fastcat.


      
Como <a <b c>> toca "a b a c"?

        
Pelo deslocamento: no ciclo c, o filho c % n é consultado como se estivesse no seu próprio ciclo c // n. O <b c> só é chamado nos ciclos 1 e 3 do pai, que para ele são 0 e 1, então alterna entre b e c.


      
Por que usar Fraction?

        
Porque as subdivisões geram terços, quintos e sétimos, que não são exatos em ponto flutuante. Com frações, tempos que deveriam coincidir coincidem exatamente, mesmo depois de muitos ciclos e aninhamentos. A conversão para float só acontece na síntese.


      
O que acontece com [a b c d] .lento(2)?

        
lento(2, p) = rapido(1/2, p). A consulta de [0, 1) vira uma consulta de p em [0, ½), que pega a e b, com tempos multiplicados por 2: a em (0, ½), b em (½, 1). No ciclo 1 tocam c e d. O padrão passa a levar 2 ciclos.


      
Como você evita estalos e distorção no áudio?

        
Estalos: envelope de 5 ms de ataque e 50 ms de release, para a onda começar e terminar em zero. Distorção: a mixagem é normalizada para pico 0,9 se passar disso, o que evita clipping no WAV de 16 bits.


      
Como você testou?

        
Com 71 testes pytest, divididos por fase: combinadores com tempos exatos, parser (precedência e erros com posição), semântica (um arquivo de exemplo por erro, cada um com a mensagem esperada) e gerador (código esperado, mais a execução do script autocontido verificando o WAV).


      
Como você adicionaria uma transformação nova, por exemplo .eco(n)?

        
A gramática não muda, porque transformacao já aceita qualquer ID com zero ou um argumento. Seriam três passos: (1) no semântico, adicionar "eco": 1 ao dicionário TRANSFORMACOES, mais a validação do argumento; (2) no runtime, criar o combinador eco(n, p), por exemplo empilhando p com cópias atrasadas e mais baixas; (3) no gerador, nada, porque expr_transformacao já gera nome(arg, P) genericamente. É uma boa resposta para mostrar que você entende a separação de fases.


      
E se quisesse elongação, tipo a@3 b (a dura 3/4)?

        
Aí a gramática muda. Seria preciso: (1) adicionar "@" NUMERO como alternativa de modificador; (2) criar o nó Peso(n, alvo) no Transformer; (3) validar no semântico que o peso é maior que 0; (4) no gerador, quando a sequência tiver pesos, emitir um combinador seq_pesos((3, A), (1, B)); (5) no runtime, implementar esse combinador, que divide o ciclo proporcionalmente aos pesos (o timecat do Tidal).


      
Quais são as limitações?

        
Consulta só pelo início do evento, sem fragmentos; não há elongação de notas; erros sintáticos param no primeiro, sem recuperação; síntese simples, sem filtros nem efeitos (que estão fora do escopo). Veja a tabela da seção 12.

Glossário

      

        
          
Token / lexemaUnidade léxica (tipo + texto). O lexema é o texto exato que casou.

          
Terminal / não terminalSímbolo que vira token (NOTA, ";") / símbolo definido por regras (camadas, faixa).

          
EBNFNotação de gramáticas com repetição { } e opcional [ ].

          
LALR(1)Parser ascendente (shift/reduce) guiado por tabela, com 1 token de lookahead.

          
Conflito shift/reducePonto em que a tabela não sabe se empilha ou reduz: sinal de gramática ambígua ou não LALR.

          
Lexer contextualLexer que só tenta os terminais aceitos no estado atual do parser.

          
Árvore de derivaçãoÁrvore concreta, um nó por regra aplicada.

          
ASTÁrvore sintática abstrata: só a estrutura com significado, com nós tipados.

          
Tabela de símbolosMapa de nomes declarados para suas informações (tipo, atributos, uso).

          
Tradução dirigida pela sintaxeCada construção da gramática tem uma regra de tradução. O resultado de um nó é montado a partir do resultado dos filhos.

          
TranspiladorCompilador cuja saída é outra linguagem de alto nível (aqui, Python).

          
CombinadorFunção que recebe padrões e devolve um padrão (seq, stack, rapido…).

          
CicloUnidade de tempo da linguagem: um compasso de 4 tempos, ou 240/bpm segundos.

          
Evento(início, fim, valor) em ciclos, com Fraction.

          
EnvelopeCurva de amplitude ao longo da nota (ataque, release).

          
ClippingAmostra além do máximo representável, que distorce o som.
